## РАЗДЕЛ 1. НАЗНАЧЕНИЕ И АРХИТЕКТУРА СИСТЕМЫ

Программный комплекс «Ак-Шумкар» представляет собой специализированную платформу корпоративного класса для автоматизированного сканирования сетей, выявления уязвимостей системного и прикладного программного обеспечения, обнаружения некорректных конфигураций, инвентаризации сетевых активов и аудита соответствия политикам безопасности.

Архитектура комплекса построена по принципу слабой связанности (Decoupled Microservices) и разделена на шесть ключевых функциональных уровней:
1. **Presentation Layer (Frontend):** Уровень обратного проксирования (Nginx) и статических бандлов (`gsa/build`). Обеспечивает отдачу SPA-приложения операторам и терминирование внешних запросов на порту 9393.
2. **Gateway & API Layer (gsad):** Демон `gsad` (порт 9392) транслирует REST/HTTP запросы веб-клиента в протокол GMP (Greenbone Management Protocol) по защищенному локальному Unix-сокету.
3. **Orchestration Layer (gvmd):** Сервис `gvmd` (Greenbone Vulnerability Management Daemon). Выполняет функции бизнес-логики: управление задачами, целями сканирования, расписаниями, пользователями и генерацией отчетов. Работает с реляционной СУБД PostgreSQL (`pg-gvm`).
4. **Execution Layer (ospd & openvasd):** Сервисы `ospd-openvas` (Python-мост по протоколу OSP) и современный Rust-демон `openvasd`. Управляют непосредственным запуском низкоуровневых процессов сканирования.
5. **Core Scanner Engine (OpenVAS Core & NASL):** Низкоуровневый движок на C (`openvas-scanner`) и интерпретатор NASL (Network Attack Scripting Language). Непосредственно отправляет сетевые пакеты, зондирует порты и проверяет наличие уязвимостей.
6. **State & Cache Layer:** Быстродействующее хранилище Redis (unix socket: `/run/redis/redis.sock`, 1025 БД) для кэширования метаданных проверок NVT и база данных PostgreSQL для долгосрочного хранения сущностей.

## РАЗДЕЛ 2. МОДЕЛЬ УГРОЗ И МЕРОПРИЯТИЯ БЕЗОПАСНОСТИ (STRIDE / LINDDUN)

Сканер уязвимостей относится к инструментам двойного назначения (Dual-Use Tools) и обладает расширенными сетевыми правами. Компрометация сканера может привести к захвату контроля над всей проверяемой сетью. В таблице ниже представлена детализированная модель угроз STRIDE и методы их нейтрализации в «Ак-Шумкар»:

| Категория | Вектор угрозы | Механизм нейтрализации (Mitigation) |
| :--- | :--- | :--- |
| **Spoofing (Спуфинг)** | Подделка запросов к openvasd REST API или GMP-протоколу; маскировка нелегитимного узла под управляющий сканер. | 1. Изоляция API внутри сети Docker Bridge.<br>2. Поддержка строгой mTLS-аутентификации с проверкой клиентских сертификатов X.509.<br>3. Заголовок X-API-KEY. |
| **Tampering (Фальсификация)** | Подмена скриптов уязвимостей NASL (Supply Chain атака); фальсификация отчетов сканирования; модификация кэша Redis. | 1. Цифровая проверка подписей фидов через встроенную Rust-утилиту feed-verifier (ключ GPG Greenbone).<br>2. Монтирование томов NVT в режиме Read-Only.<br>3. Доступ к Redis только через сокет с правами 770. |
| **Repudiation (Отказ от авторства)** | Отказ оператора от факта запуска сканирования критической инфраструктуры, повлекшего сбой сервисов. | 1. Неизменяемый структурированный аудит в PostgreSQL с фиксацией User ID, IP-адреса, времени и параметров цели.<br>2. Журналирование gvmd и openvas.log. |
| **Information Disclosure (Утечка данных)** | Утечка сетевых карт, сведений об обнаруженных CVE и паролей LSC (Local Security Checks: SSH, SMB, ESXi). | 1. Шифрование учетных записей аудита в СУБД (AES-256).<br>2. Запрет публикации портов СУБД наружу.<br>3. Санация HTML через dompurify во фронтенде (защита от Stored XSS). |
| **Denial of Service (Отказ в обслуживании)** | Сбой проверяемых систем (BSOD, падение сетевых демонов) или исчерпание памяти сканера (OOM Killer). | 1. Профилирование сканирования: жесткие ограничения max_hosts и max_checks.<br>2. Предварительный Alive-test (ICMP/TCP-SYN) перед атакой.<br>3. Лимиты памяти в Docker Compose. |
| **Elevation of Privilege (Эскалация привилегий)** | Эксплуатация RCE в NASL-интерпретаторе или парсерах pcap/tcp для выхода из контейнера на хост-сервер. | 1. Миграция интерпретатора и сетевого парсера на безопасный по памяти Rust.<br>2. Минимизация Linux Capabilities: запуск от пользователя gvm, запрет лишних флагов. |

## РАЗДЕЛ 3. СИСТЕМНЫЕ ТРЕБОВАНИЯ И ПОДГОТОВИТЕЛЬНЫЙ ЭТАП

### 3.1. Аппаратные требования
В связи с тем, что база уязвимостей насчитывает более 100 000 проверок безопасности NASL, а процесс загрузки требует их декомпрессии и кэширования в оперативной памяти и PostgreSQL, к серверу предъявляются следующие требования:

| Параметр | Минимальная конфигурация | Рекомендуемая (Enterprise) |
| :--- | :--- | :--- |
| **Процессор (CPU)** | 4 ядра (x86_64, от 2.4 ГГц) | 8–16 ядер (x86_64 с поддержкой AVX2) |
| **Оперативная память (RAM)** | 16 ГБ (критический минимум) | 32–64 ГБ ECC RAM (для параллельных сканов) |
| **Дисковая подсистема** | 60 ГБ свободного места на SSD | 250+ ГБ NVMe SSD (IOPS не менее 5000) |
| **Сетевой интерфейс** | 1 Гбит/с Ethernet | 10 Гбит/с Ethernet (при сканировании сегментов /16) |

> [!CAUTION]
> **ВНИМАНИЕ ПО ДИСКОВОЙ ПОДСИСТЕМЕ:** Использование обычных магнитных жестких дисков (HDD) категорически не рекомендуется. Низкая скорость случайного чтения приведет к зависанию демона `gvmd` на этапе инициализации баз уязвимостей (SCAP/NVT).

### 3.2. Программные требования
- **Поддерживаемые операционные системы:** Debian GNU/Linux 11 (Bullseye) / 12 (Bookworm), Ubuntu Server 22.04 / 24.04 LTS, Rocky Linux 9, либо Windows Server 2022 / Windows 11 с установленной подсистемой WSL2.
- **Среда контейнеризации:** Docker Engine версии 24.0.0 и новее, Docker Compose Plugin V2.
- **Сетевые доступы:** Доступ к официальным реестрам образов (`registry.community.greenbone.net` или локальному зеркалу) и серверам синхронизации фидов по протоколам HTTP/HTTPS и Rsync (порт 873).

## РАЗДЕЛ 4. ПОШАГОВАЯ ИНСТРУКЦИЯ ПО РАЗВЕРТЫВАНИЮ И УСТАНОВКЕ (GIT-МЕТОД)

Развертывание системы «Ак-Шумкар» по базовому сценарию выполняется по шести последовательным шагам на целевом сервере:

### Шаг 1. Подготовка исходного кода
Перейдите в директорию проекта на диске (или выполните клонирование репозитория на целевой Linux-хост):
```bash
# На сервере Linux:
git clone https://github.com/Artorias21/ak-shumkar-VM.git /opt/ak-shumkar-VM
cd /opt/ak-shumkar-VM

# На рабочей станции Windows:
cd D:\888000131\ak-shumkar-VM
```

### Шаг 2. Сборка оптимизированного локального образа сканера (openvasd-local)
В сервисе openvasd используется оптимизированный контейнерный образ, собирающий современное Rust-ядро openvasd и C-библиотеки gvm-libs:
```bash
# Сборка контейнера через multi-stage Dockerfile:
docker build -f .docker/prod.Dockerfile -t openvasd-local .
```

### Шаг 3. Сборка веб-интерфейса GSA (Single Page Application)
Пользовательский веб-интерфейс компилируется из TypeScript/React в статический production-бандл:
```bash
# Вариант 1 (при наличии установленного Node.js >= 20 на хосте):
cd gsa
npm install
npm run build
cd ..

# Вариант 2 (изолированная сборка в Docker, если Node.js не установлен):
docker run --rm -v "%cd%/gsa:/app" -w /app node:20-alpine sh -c "npm install && npm run build"
```
Результатом сборки является каталог `gsa/build/`, содержащий скомпилированный `index.html`, JS/CSS бандлы в директории `assets/` и статические изображения.

### Шаг 4. Запуск продуктового стека контейнеров
Запуск осуществляется единой командой оркестратора:
```bash
docker compose -f docker-compose.full.yml up -d
```
Проверка состояния контейнеров:
```bash
docker compose -f docker-compose.full.yml ps
```

> [!NOTE]
> **Особенности инициализирующих контейнеров:** Контейнеры синхронизации баз (`vulnerability-tests`, `notus-data`, `scap-data`, `cert-bund-data`, `dfn-cert-data`, `data-objects`, `report-formats`) являются однократными задачами (init-containers). Они копируют данные в тома и переходят в состояние `Exited (0)`. Это штатный режим работы.

### Шаг 5. Инициализация учетной записи администратора
После запуска сервиса `gvmd` создайте суперпользователя в базе данных:
```bash
# Создание администратора с надежным паролем:
docker compose -f docker-compose.full.yml exec -u gvmd gvmd gvmd --create-user=admin --new-password="AdminAkShumkar2026!"

# Команда для смены пароля в будущем:
docker compose -f docker-compose.full.yml exec -u gvmd gvmd gvmd --user=admin --new-password="НовыйПароль2026!"
```

### Шаг 6. Мониторинг синхронизации фидов уязвимостей
При первом запуске `gvmd` выполняет загрузку более 100 000 тестов безопасности в БД PostgreSQL. Этот процесс занимает от 20 до 50 минут в зависимости от скорости диска. Отслеживайте статус по логам:
```bash
docker compose -f docker-compose.full.yml logs -f gvmd
```
Система готова к проведению сканирований после появления в журнале записей: `Updating VTs in database... done` и `SCAP sync: finished`.

## РАЗДЕЛ 5. РУКОВОДСТВО ОПЕРАТОРА ПО ЭКСПЛУАТАЦИИ

### 5.1. Первичный вход в систему
- **Адрес веб-интерфейса:** `http://<IP_АДРЕС_СЕРВЕРА>:9393` (или `http://localhost:9393` при локальном запуске).
- **Учетные данные:** логин `admin`, пароль, заданный на Шаге 5.
- **Контроль состояния баз:** меню `Administration` -> `Feed Status`. Все разделы (NVT, SCAP, CERT) должны отображать актуальную дату обновления.

### 5.2. Порядок создания и проведения сканирования
1. **Настройка учетных данных для аудита (опционально):**
   Перейдите в `Configuration` -> `Credentials`. При необходимости проведения инвентаризации конфигураций ОС и ПО добавьте SSH-ключи (для Linux) или учетную запись домена/локального администратора SMB (для Windows).
2. **Создание цели сканирования (Target):**
   Перейдите в `Configuration` -> `Targets`. Нажмите `New Target`. Укажите наименование, список IP-адресов или подсетей (например, `192.168.1.0/24`), диапазон портов (по умолчанию `All IANA assigned TCP and UDP`) и метод проверки доступности (Alive Test: ICMP Ping, TCP-SYN).
3. **Формирование задачи (Task):**
   Перейдите в `Scans` -> `Tasks`. Нажмите `New Task`. Задайте имя задачи, выберите созданный ранее Target и укажите профиль сканирования (Scan Config). Рекомендуемый профиль: `Full and fast` (комплексный аудит сетевых служб без деструктивных тестов).
4. **Запуск и мониторинг:**
   Нажмите иконку `Play` (Start) в строке созданной задачи. В столбце `Status` будет отображаться текущий процент выполнения сканирования.
5. **Выгрузка и анализ отчетов:**
   После завершения перейдите в `Scans` -> `Reports`. Отчет содержит перечень найденных уязвимостей с оценкой критичности по шкале CVSS (v2/v3), описание эксплоитов, ссылки на CVE и рекомендации по устранению. Доступен экспорт в PDF, XML, CSV.

## РАЗДЕЛ 10. ДОСКОНАЛЬНОЕ РУКОВОДСТВО ПО КОММЕРЧЕСКОЙ СИСТЕМЕ ЛИЦЕНЗИРОВАНИЯ И ЗАЩИТЫ «АК-ШУМКАР» (SKYSOC V-3.4)

В производственной ветке `feature/skysoc-branding` приватного репозитория `https://github.com/Malfade/ak-shumkar-VM.git` (коммиты релизов V-3.3 и V-3.4) реализован собственный модуль криптографической защиты, ограничения срока использования (Time-bound Licensing) и аппаратной привязки сканера при поставках заказчикам.

### 10.1. Архитектура и компоненты подсистемы лицензирования
Подсистема лицензирования решает задачу монетизации и контроля распространения системы «Ак-Шумкар», предотвращая несанкционированное копирование и использование сканера после окончания оплаченного периода (3, 6 или 12 месяцев).

**Структура каталогов и скриптов подсистемы:**
- `PRODUCTION_LICENSE_AND_ACCESS.md` — официальная спецификация протокола лицензирования и харднинга сервера.
- `security/licensectl.sh` — клиентская утилита проверки, верификации и установки лицензии на хосте заказчика.
- `vendor/licensing/license-vendorctl.sh` — закрытая внутренняя утилита вендора (производителя) для генерации мастер-ключей RSA и выпуска подписанных лицензий заказчикам.
- `licenses/public.pem` — открытый ключ RSA (4096-bit), поставляемый в дистрибутиве сканера.
- `licenses/license-maltop-3m.json (+ .sig)` — эталонный образец валидной лицензии с открепленной подписью.
- `start.sh` — центральный скрипт запуска, выполняющий строгую проверку лицензии ДО старта Docker-контейнеров.
- `scannerctl.sh` — единый CLI-интерфейс оператора (команды: `license`, `license-vendor`, `harden`, `deploy`, `disable`).

### 10.2. Формат лицензионного файла (JSON Schema v1)
Лицензия представляет собой строго структурированный JSON-документ, канонизированный без пробелов и с сортировкой ключей по алфавиту для обеспечения детерминированного хеширования SHA-256:

```json
{
  "customer_id": "acme-corp",
  "expires_at": "2026-12-31T23:59:59Z",
  "instance_id": "a14ad03db7b140e58b75a127594b8f7b",
  "issued_at": "2026-06-01T00:00:00Z",
  "license_id": "67c7b1a8-bb5f-48bf-ab5a-93d8c7d3a9a4",
  "plan_months": 6,
  "product": "ak-shumkar-vm",
  "schema_version": 1
}
```

**Описание полей лицензии:**
1. `customer_id` (string) — уникальный идентификатор компании-заказчика.
2. `expires_at` (ISO 8601 UTC) — дата и время окончания действия лицензии. По наступлении этого времени запуск сканера блокируется.
3. `instance_id` (string, опционально) — аппаратная привязка к хосту (`/etc/machine-id`). Если поле заполнено, лицензия работает ИСКЛЮЧИТЕЛЬНО на сервере с данным machine-id; при переносе на другой сервер запуск блокируется.
4. `issued_at` (ISO 8601 UTC) — дата генерации лицензии.
5. `license_id` (UUID v4) — уникальный идентификатор лицензионного сертификата.
6. `plan_months` (int) — срок действия тарифа (3, 6, 12 месяцев).
7. `product` (string) — признак продукта ("ak-shumkar-vm").

### 10.3. Криптографический алгоритм верификации
Для защиты от подделки лицензии используется асимметричная криптография RSA с длиной ключа 4096 бит:
1. **Генерация подписи:** JSON-файл лицензии канонизируется утилитой `python3` (сортировка ключей), после чего вычисляется дайджест SHA-256 и подписывается приватным ключом вендора (`private.pem`) командой:
   `openssl dgst -sha256 -sign private.pem -out license.json.sig license.json`
2. **Проверка подписи:** При старте системы скрипт `start.sh` извлекает публичный ключ `licenses/public.pem` и выполняет верификацию подписи через:
   `openssl dgst -sha256 -verify public.pem -signature license.json.sig canonical_license.json`
3. **Контроль срока:** Если подпись верна, Python-парсер сравнивает текущее системное время с `expires_at` в UTC. Если `exp <= now`, возвращается код возврата 2 (License expired), и старт стека аварийно прерывается.
4. **Контроль хоста:** Если в лицензии указан `instance_id`, парсер считывает файл `/etc/machine-id`. При несовпадении возвращается код 3 (Instance mismatch), и запуск блокируется.

### 10.4. Практические регламенты и команды управления

#### Регламент А. Выпуск лицензии производителем (Вендор):
Операция выполняется на доверенном изолированном компьютере разработчика. Приватный ключ `private.pem` **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** передавать заказчику или копировать на боевой сервер!

```bash
# 1. Первичная генерация пары ключей вендора (выполняется один раз):
./scannerctl.sh license-vendor gen-keys
# Будут созданы vendor/licensing/output/private.pem и public.pem

# 2. Выпуск коммерческой лицензии клиенту на 6 месяцев:
./scannerctl.sh license-vendor issue --customer-id "Bank-Kyrgyzstan" --months 6

# 3. Выпуск лицензии с жесткой привязкой к конкретному серверу заказчика:
./scannerctl.sh license-vendor issue --customer-id "MIA-KR" --months 12 --instance-id "a14ad03db7b140e58b75a127594b8f7b"
# В результате генерируются 2 файла для передачи заказчику:
# - license-Bank-Kyrgyzstan-6m.json
# - license-Bank-Kyrgyzstan-6m.json.sig
```

#### Регламент Б. Установка лицензии на целевом сервере (Клиент):
Файлы лицензии устанавливаются в защищенную системную директорию `/etc/ak-shumkar/license/` с правами доступа `root:root (0644)`:

```bash
# 1. Установка лицензии и подписи в систему:
sudo ./scannerctl.sh license install \
  --license-file ./licenses/license-Bank-Kyrgyzstan-6m.json \
  --signature-file ./licenses/license-Bank-Kyrgyzstan-6m.json.sig

# 2. Проверка статуса, валидности подписи и остатка дней:
./scannerctl.sh license status
# Вывод команды:
# ✅ Signature is valid.
# license_id  : 67c7b1a8-bb5f-48bf-ab5a-93d8c7d3a9a4
# customer_id : Bank-Kyrgyzstan
# plan_months : 6
# issued_at   : 2026-11-10T12:00:00Z
# expires_at  : 2027-05-10T12:00:00Z
# status      : active (181 days left)
```

#### Регламент В. Аварийный запуск без лицензии (Bypass):
В случае экстренной необходимости запуска комплекса при просроченной лицензии (например, в ходе устранения аварии) предусмотрен сервисный флаг:
```bash
ALLOW_EXPIRED_LICENSE=1 ./start.sh
# Либо через scannerctl:
ALLOW_EXPIRED_LICENSE=1 ./scannerctl.sh deploy
```

### 11.5. Профиль повышенной безопасности (Host Access Hardening)
Для полного соответствия enterprise-требованиям безопасности в контуре заказчика рекомендуется применить харднинг доступа:
```bash
sudo ./scannerctl.sh harden --admin-user <администратор_linux>
```
*Эффект применения:*
- Создается выделенный непривилегированный сервисный аккаунт `scanner` без shell-доступа;
- Доступ по SSH жестко ограничивается только указанным административным аккаунтом;
- В `sshd_config` отключаются `PermitRootLogin` и `PasswordAuthentication` (вход только по SSH-ключам).
