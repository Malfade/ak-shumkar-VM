# Полный аудит системы: OpenVAS Scanner (акцент на White-label VM)

Данный документ представляет собой полный архитектурный и компонентный аудит системы, основанный на структуре репозитория. Особое внимание уделено взаимодействию с Frontend-слоем и обеспечению Enterprise Security.

---

## 1. Общая архитектура системы (High-Level Architecture)

Система представляет собой гибридную архитектуру с переходом от унаследованного C-кода к современному Rust-стеку. 
Главная задача системы — управление жизненным циклом сканирования уязвимостей (Vulnerability Management), исполнение NASL-скриптов и предоставление интеграционного слоя для внешних оркестраторов и пользовательских интерфейсов (UI).

- **Legacy C-слой** (`src/`): Отвечает за низкоуровневые сетевые операции, управление пулом процессов сканирования и загрузку плагинов.
- **Rust-слой** (`rust/`): Современное ядро, консолидирующее `openvas-scanner`, `ospd-openvas` и `notus-scanner`. Обеспечивает безопасный API, работу с хранилищем, верификацию фидов (Feeds) и интерпретацию NASL-скриптов.

---

## 2. Анализ Frontend-слоя и интеграции (Frontend / API Interface)

В самом репозитории **физически отсутствует классический Frontend (HTML/JS/React/Vue)**. Пробежав по всем директориям и проверив исходный код демона `openvasd`, я подтверждаю: это **headless (безголовый)** сканер.

Здесь нет панели управления с графиками, к которой можно было бы привыкнуть в Greenbone Community Edition.

### Ответственные компоненты:
1. **HTTP Daemon (`rust/src/openvasd/`)**:
   - Является чистым API-сервером на Rust (использует `hyper`).
   - Не отдает статические файлы (HTML/CSS) и не имеет встроенного Swagger UI.
   - Точка входа для всех UI и внешних систем.
   - Реализует REST HTTP API для создания и запуска сканирований, агрегации результатов и управления настройками.
2. **API Contract (`rust/doc/openapi.yml`)**:
   - Строгий Swagger/OpenAPI контракт, определяющий форматы запросов (JSON) и ответов.
   - Включает endpoints: `/health`, `/scans`, `/vts` (Vulnerability Tests), `/notus`.
   - **Это и есть ваш "фронтенд-интерфейс"** — база, на которой вы должны строить свой White-label UI.

### Практики Enterprise Security на стыке с Frontend:
Для построения безопасного UI поверх данного API необходимо реализовать следующее:
- **Аутентификация API**: `openvasd` поддерживает **API Key** (в заголовке `X-API-KEY`) и **mTLS (Client Certificates)**. Для production-инсталляций mTLS является обязательным между UI-сервером и `openvasd`.
- **Защита от инъекций (XSS/SQLi)**: Все данные, возвращаемые из NASL-плагинов или сканирования (результаты), должны проходить строгую санацию (sanitize) при рендеринге во Frontend-компонентах. Сам API отдаёт сырые JSON-данные.
- **Rate Limiting & ACL**: Рекомендуется закрывать `openvasd` внутренним API-шлюзом (например, Nginx/Kong/Envoy) для обеспечения Rate Limiting, защиты от DDoS и реализации ролевой модели (RBAC).
- **Transport Security**: HSTS, строгие политики TLS (>= 1.2), запрет прямых HTTP-подключений.

## 3. Core Backend & Orchestration (Ядро управления)

- **`rust/src/scannerctl/`**: CLI-утилита инженера. Используется для управления обновлениями баз (Feeds), отладки NASL-скриптов и трансформации конфигураций. Отвечает за интеграцию системы с CI/CD или Cron-задачами VM.
- **`rust/src/scheduling/`** (Планировщик): Модуль для управления очередью сканирований и распределением нагрузки.

**Риски и рекомендации**: При высоких нагрузках (тысячи сканирований) планировщик должен поддерживать шардирование (Sharding) и горизонтальное масштабирование через брокеры очередей.

---

## 4. Движок сканирования (Scanner & Execution Engine)

Самая критичная с точки зрения стабильности часть системы, исполняющая проверки безопасности (VTs).

- **`rust/src/nasl/`**: Подсистема NASL (Network Vulnerability Scripting Language).
  - Включает написанный на Rust синтаксический анализатор (AST), интерпретатор и встроенные функции (сеть, криптография, ssh, http).
- **`src/` (Legacy C)**: Содержит логику управления процессами (`processes.c`), низкоуровневые сетевые атаки (`attack.c`) и старый планировщик плагинов (`pluginscheduler.c`).
- **`rust/src/alive_test/`**: Проверка достижимости хостов (ICMP, TCP-SYN/ACK, ARP Ping) перед полным сканированием (повышает скорость работы).

**Архитектурное решение**: Перенос интерпретатора NASL на Rust значительно снизил риски RCE (Remote Code Execution) и проблем с памятью (Buffer Overflows), типичных для C.

---

## 5. Хранение данных и управление контентом (Data & State)

- **`rust/src/storage/`**: Слой абстракции над хранилищем. Поддерживает Redis (основной для состояния и кэша сканов), In-memory (для тестов) и Infisto.
- **`rust/src/feed/` & `rust/src/feed_verifier/`**: Подсистема жизненного цикла базы уязвимостей. Автоматизирует загрузку, проверку цифровых подписей (GPG/сигнатуры) для защиты от Supply Chain атак.
- **`rust/src/notus/`**: Локальный сканер для парсинга package-листов (advisories) и определения уязвимостей ОС без активного сетевого сканирования.

**Безопасность хранения**: БД Redis не должна торчать наружу. Соединения к кешу/storage должны аутентифицироваться и, по возможности, шифроваться (TLS in Redis).

---

## 6. Инфраструктура и DevOps (Infrastructure)

- **`compose/` && `.docker/`**: Наборы Docker Compose файлов и Dockerfile для сборки контейнеров, обеспечения воспроизводимости среды.
- **`charts/`**: Helm-чарты для развертывания в Kubernetes кластерах.

Обеспечивает лёгкий CI/CD pipeline. В рамках White-label продукта на их основе должны строиться собственные cloud-init / Packer сборки или K8s операторы.

---

## 7. Резюме: Зоны ответственности (Summary)

| Компонент / Директория | Роль в системе | Примечание |
|---|---|---|
| **API Contract** (`doc/openapi.yml`) | **Frontend-интерфейс** | Контракт взаимодействия для White-label UI |
| **BFF API** (`rust/src/openvasd/`) | Обработка HTTP, Auth, Scans | Изолировать от прямого интернета |
| **Logic/CLI** (`rust/src/scannerctl/`) | Управление фидами, отладка | Использовать в cron/orchestrator |
| **Execution** (`rust/src/nasl/`, `src/`) | Исполнение проверок и эксплоитов | Песочница, лимитирование ресурсов |
| **Storage** (`rust/src/storage/`) | Хранение текущих сканов (Redis) | Обязательная защита базы/пароли |
| **Infra** (`charts/`, `compose/`) | Развертывание | Точка кастомизации под бренд |

## 8. Архитектурные рекомендации по запуску White-label продукта

1. **Разделение инфраструктуры**: Вынести БД (Redis) и очередь задач на отдельные изолированные серверы/managed-сервисы с настроенным резервным копированием.
2. **Нулевое доверие (Zero Trust) на Frontend-слое**: Построить UI таким образом, чтобы он обменивался с `openvasd` только по внутреннему VPN или Service Mesh.
3. **Audit Trails**: Реализовать внешнее глубокое логирование (в ELK/Splunk) всех действий API через `openvasd` для расследования инцидентов.
4. **Валидация Feeds**: Настроить собственное зеркало (Mirror) фидов для защиты от блокировок vendor'а и обеспечения 100% доступности апдейтов.
